# Development practice: when slicing a large change or verifying a UI change

- Start with the reported behavior and reproduce it. Find the shared entry point and existing tests before choosing a fix; keep the same seeded map and combat and preserve released saves.
- Split large work into vertical slices that each leave a working, reviewable game: for example, one screen and its interaction, then the next screen. Define the behavior and acceptance check for each slice, avoid half-wired controls, and keep each slice building and testing. If the job cannot be finished in one pass, report `partial` and name the remaining slices.
- Test behavior at the boundary that matters: demonstrate the regression before a code fix and test the fixed outcome afterward. Run the repository's required build and tests; for run or combat changes also obtain the required balance evidence. Do not change thresholds to make a check pass.
- For visual work, build and open the actual built game in a headless browser if available. At 390px and 1280px, inspect screenshots of the changed screen and relevant states, then interact as a player: select, navigate, pause, and use keyboard focus as applicable. Check a short mobile height, long content, readable controls, overflow and page scroll. A passing DOM assertion is not a visual inspection.
- If a preview server cannot bind, try an already available browser automation tool with request interception: serve requests for a synthetic origin from the built `dist` files in the route handler, return correct MIME types, and abort all other origins. Resolve paths inside `dist` and reject traversal and symlinks escaping it. This needs no listening port; it still needs a working browser and interception API. Do not install packages or access the network to obtain one. An example with an available Playwright API is `page.route('**/*', handler)`, where the handler fulfills only the synthetic origin from `dist` and aborts everything else. Verify the game and assets loaded before inspecting; a blank page is not evidence.
- For a fight-state finding, reach a real fight, capture and inspect both running and paused states at each requested width and a short phone height, and check the pause control, status, wrapping, clipping and page scroll. Record the inspected commit, dimensions, state and screenshot locations. Host screenshots cover only the states they actually show; do not infer other states or commit identity from their filenames. If the browser or evidence is unavailable, report the specific missing checks rather than declaring the finding resolved.
- Record the commands, viewport sizes, screens and states inspected, and any unavailable checks or failures. Fix visible defects and inspect again after the fix. Keep screenshots or other verification artifacts out of the product unless requested.
